ES Modules in Depth

ES Modules are the official standard for sharing code between JS files. Mastering their subtleties — live bindings, tree-shaking, barrels, and dynamic imports — is essential for writing scalable, production-ready JavaScript.

Topic 1: Named vs Default Exports — Best Practices

Named exports are auto-completable and refactor-safe; tooling can track renames. Default exports are for a file that has one main thing to offer — but the name is chosen by the importer, which is a common source of bugs.

// utils.js — named exports (many per file, auto-completable)
export function formatPrice(p) { return `₹${p}`; }
export function gst(p, rate = 18) { return p * rate / 100; }
export const TAX_RATE = 18;

// main.js — named import
import { formatPrice, gst, TAX_RATE } from "./utils.js";
console.log(formatPrice(100));   // ₹100
console.log(gst(100));           // 18

// Card.js — single default export (one hero per file)
export default function Card({ title }) { /* ... */ }

// main.js — any name works on default import (common bug source!)
import Card     from "./Card.js";      // ✓ conventional
import Whatever from "./Card.js";      // ✓ also valid — but confusing!
AspectNamedDefault
Auto-completable✓✗
RenamingTracked by toolingManual
Tree-shakingBetterSlightly worse
Multiple per fileManyOnly one
Best forUtilities, hooks, helpersA single hero per file

Topic 2: Aliasing & Namespace Imports

Use as to rename on import or export. Use import * to pull everything into a single namespace object — handy for dynamic key lookup, but it defeats tree-shaking.

// Rename on import
import { formatPrice as fp } from "./utils.js";
fp(100);   // same as formatPrice(100)

// Rename on export (re-export with alias)
export { formatPrice as format } from "./utils.js";

// Namespace — all exports under one object
import * as utils from "./utils.js";
console.log(utils.formatPrice(100));  // ₹100
console.log(utils.gst(100));          // 18
console.log(utils.TAX_RATE);          // 18

// Follow-along — what logs?
// utils.js:  export const a = 1;  export const b = 2;
// main.js:   import * as u from "./utils.js";
console.log(u.a + u.b);  // → 3
console.log(u.c);          // → undefined  (c doesn't exist)

⚠️ import * defeats tree-shaking when you access exports by computed key: utils[someName]() — the bundler can't know which exports are unused.

Topic 3: Barrel Files — Single Import Path

A barrel is an index.js that re-exports from multiple files, so consumers get everything from one clean path instead of many deep paths.

// components/index.js — the barrel
export { default as Button } from "./Button.js";
export { default as Card }   from "./Card.js";
export { default as Modal }  from "./Modal.js";

export * from "./hooks.js";                        // re-export ALL named
export { useForm, useDebounce } from "./hooks.js"; // selective re-export

// App.js — one import instead of three
import { Button, Card, Modal } from "./components";

// Without the barrel you'd write:
// import Button from "./components/Button.js";
// import Card   from "./components/Card.js";
// import Modal  from "./components/Modal.js";

⚠️ A poorly tree-shaken barrel can pull in code you never used. Modern bundlers handle it; be careful when authoring libraries.

Topic 4: Dynamic import()

import() returns a Promise that resolves to the module namespace. Use it for code-splitting, lazy-loading heavy dependencies, or conditional loading.

// Static — parsed and loaded before any code in this file runs
import { gst } from "./utils.js";

// Dynamic — loaded on demand, returns a Promise
async function showSettings() {
  const { Settings } = await import("./Settings.js");
  Settings.render();
}

// Conditional — only download the big library when the user needs it
button.addEventListener("click", async () => {
  const Chart = await import("./BigChartLibrary.js");
  Chart.draw();
});

// React.lazy uses dynamic import() under the hood
const Settings = React.lazy(() => import("./Settings.js"));

Topic 5: Live Bindings & Singletons

Imported bindings are live — when the exporting module updates a let variable, all importers see the new value. They are also read-only — you cannot reassign an imported binding directly.

// counter.js
export let count = 0;
export function inc() { count++; }

// main.js
import { count, inc } from "./counter.js";
console.log(count);   // 0
inc();
console.log(count);   // 1  ← live binding — sees the update

count = 99;           // TypeError — imports are read-only

// Singleton: every importer of the same module gets the SAME instance
// cache.js
const cache = new Map();
export default cache;

// Any file — they all share the SAME Map object
import cache from "./cache.js";
cache.set("user:1", { name: "Priya" });   // visible everywhere

Topic 6: Circular Dependencies

When A imports from B and B imports from A, one side will see undefined at module top level because the other hasn't finished evaluating yet. Fix by extracting the shared value to a third module, or by reading the value inside a function (lazy access).

// a.js
import { fromB } from "./b.js";
export const fromA = "I am A";
console.log("a sees fromB =", fromB);   // may be undefined at first run

// b.js
import { fromA } from "./a.js";
export const fromB = "I am B";
console.log("b sees fromA =", fromA);   // may be undefined

// Fix 1 — move shared value to shared.js; both a.js and b.js import from it
// Fix 2 — lazy access: read fromB inside a function, not at module top level
// Fix 3 — ESLint plugin import/no-cycle to catch these automatically

Topic 7: Bundlers — Webpack, Vite, Rollup

Bundlers walk your import graph, tree-shake unused exports, merge and minify output, and split chunks at each import() call. Pick the right tool for the job.

// What every bundler does:
// 1. Read entry file (e.g. main.js)
// 2. Walk the import graph — find every imported module recursively
// 3. Tree-shake — drop exports that are never imported
// 4. Combine + minify — merge into one or more bundles
// 5. Split chunks — each dynamic import() becomes a separate lazy chunk
// 6. Generate sourcemaps — map minified code back to original source
ToolBest forStrengths
ViteModern frontendsLightning-fast dev (esbuild), Rollup prod build
WebpackEstablished big appsMature, plugin-rich
RollupLibrariesCleanest tree-shaking, smallest output
esbuildSpeedInsanely fast, simpler config
ParcelZero-config simple appsAuto-discovery
