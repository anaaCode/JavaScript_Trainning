The Event Loop

JavaScript runs on a single thread — one call stack, one statement at a time. The event loop is the tiny algorithm that decides what runs next, giving JS its non-blocking superpower without ever leaving that single thread.

Topic 1: JavaScript is Single-Threaded

JS has one call stack. Async work is delegated to the runtime (browser Web APIs or Node's libuv). When that work finishes, the callback lands on a queue. The event loop pulls it onto the stack only when the stack is completely empty.

// Everything runs on ONE thread — there is no parallelism inside JS itself.
// Async work (timers, fetch, events) is handled OUTSIDE the engine,
// then re-entered via the queues when the stack is free.

console.log("start");          // runs on the stack immediately
setTimeout(() => {
  console.log("timer");        // delegated to Web API → lands in macrotask queue
}, 1000);
console.log("end");            // runs on the stack immediately

// Output: start → end → (1 second later) timer

Topic 2: The Runtime Architecture

The JS engine (V8) contains the call stack and heap. Outside it, the runtime provides Web APIs (timers, fetch, DOM events) that handle async work. Completed async work is fed into one of two queues — microtask or macrotask — and the event loop bridges them back to the stack.

// Mental model of the runtime:
//
//  ┌─────────────────────────────────┐
//  │         JS Engine (V8)          │
//  │  ┌──────────┐  ┌──────────┐    │
//  │  │  Stack   │  │   Heap   │    │
//  │  └──────────┘  └──────────┘    │
//  └─────────────────────────────────┘
//              ▲
//              │  Event Loop pulls
//              │
//  ┌───────────────────────┐    ┌──────────────┐
//  │   Microtask Queue     │ ←  │   Web APIs   │
//  │  (Promise.then, ...)  │    │ (timers,     │
//  └───────────────────────┘    │  fetch, DOM) │
//  ┌───────────────────────┐    │              │
//  │   Macrotask Queue     │ ←  │              │
//  │  (setTimeout, I/O...) │    └──────────────┘
//  └───────────────────────┘

Topic 3: What the Event Loop Does

The event loop runs one tiny algorithm forever: wait for the stack to empty, drain every microtask, then take exactly one macrotask and repeat. Three rules: microtasks have priority; all microtasks drain before any macrotask runs; only one macrotask runs per iteration.

// Event loop algorithm (simplified):
//   1. Wait for call stack to be empty
//   2. Drain ALL microtasks (every single one, including newly added ones)
//   3. Take ONE macrotask → run it on the stack
//   4. Go back to step 1

// This loop runs forever as long as the page/process is alive.

Topic 4: Why setTimeout(0) Runs Last

setTimeout(fn, 0) does not mean "run now" — it means "queue this as a macrotask as soon as the delay expires". Sync code runs first, then all microtasks drain, and only then does the macrotask queue get a turn.

console.log("1");                                 // sync
setTimeout(() => console.log("2"), 0);            // macrotask queue
Promise.resolve().then(() => console.log("3"));   // microtask queue
console.log("4");                                 // sync

// Output: 1, 4, 3, 2
//
// Step by step:
//   Stack  → "1", "4"    (sync code runs top-to-bottom)
//   Microtasks → "3"     (drained completely before any macrotask)
//   Macrotasks → "2"     (one macrotask, then loop restarts)
//
// "3" beats "2" even though both were scheduled at the same time.

Topic 5: Microtask vs Macrotask

Knowing which queue a callback lands in determines its execution order. Microtasks always flush completely before the next macrotask runs — even microtasks scheduled during the current microtask drain.

// MICROTASKS — high priority, drain completely each loop tick
//   Promise.then / .catch / .finally
//   queueMicrotask(fn)
//   MutationObserver callbacks
//   await continuations (same as .then)

// MACROTASKS — one per loop tick, lower priority
//   setTimeout / setInterval
//   setImmediate (Node.js only)
//   I/O callbacks
//   UI events (click, input, etc.)
//   requestAnimationFrame

console.log("A");

setTimeout(() => console.log("B"), 0);           // macrotask

Promise.resolve()
  .then(() => console.log("C"))                  // microtask 1
  .then(() => console.log("D"));                 // microtask 2 (scheduled when C runs)

queueMicrotask(() => console.log("E"));          // microtask 3

console.log("F");

// Output: A, F, C, E, D, B
//
// Sync:       A, F
// Microtasks: C → schedules D; then E; then D  (all drain before B)
// Macrotask:  B

Topic 6: Don't Block the Loop

Because JS is single-threaded, any long-running synchronous code freezes the entire page — timers won't fire, clicks won't register, animations stop. The blocked call stack prevents the event loop from processing anything.

function blockFor(ms) {
  const t0 = Date.now();
  while (Date.now() - t0 < ms) {}   // busy-wait — holds the stack hostage
}

setTimeout(() => console.log("timer"), 0);
blockFor(3000);                       // freezes everything for 3 seconds
console.log("after block");

// Output:
//   (3-second freeze — tab is completely unresponsive)
//   after block
//   timer
//
// The timer was ready at 0ms but couldn't run until the stack cleared at ~3000ms.
// Solution: break heavy work into chunks (setTimeout), or move it to a Web Worker.

Topic 7: Practical Implications

Understanding the event loop shapes everyday coding decisions — from UI update ordering to why await behaves like .then, to avoiding page freezes in loops.

// 1. Promise callbacks beat timers — use this for ordering UI updates
someAsyncWork()
  .then(updateUI);           // guaranteed to run before next macrotask

// 2. await is a microtask — same priority as .then
async function demo() {
  console.log("before await");
  await Promise.resolve();
  console.log("after await");  // microtask continuation
}
setTimeout(() => console.log("timer"), 0);
demo();
// Output: before await → after await → timer

// 3. Breaking up heavy sync work — yield to the event loop between chunks
function processChunk(items, index) {
  const end = Math.min(index + 1000, items.length);
  for (let i = index; i < end; i++) {
    // process items[i]
  }
  if (end < items.length) {
    setTimeout(() => processChunk(items, end), 0);  // yield, then continue
  }
}
